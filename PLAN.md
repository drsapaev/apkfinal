## Ключевые инварианты (зафиксированы тестами)

1. **Маршрут записи определяется владельцем**, а не наличием doctorId:
   пациент → `mobile/book`, сотрудник → `POST /appointments`. Повтор offline-операции
   идёт по исходному маршруту (`CREATE_APPOINTMENT_SELF` / `CREATE_APPOINTMENT_STAFF`).
2. **Серверный отказ не порождает вторую операцию** (нет API-fallback).
3. **Результат записи — трёхсостоянийный**: `Confirmed` / `Queued` / `Rejected`;
   `403/409/422` никогда не классифицируются как «нет сети».
4. **Анализ нигде не отображается как диагноз/назначение**; не-EMR-черновики помечены явно.
5. **Отказ сервера не создаёт живой талон** — очередь оперируется только через сервер.

## Как проверить (приёмка)

Единица: `./gradlew testDebugUnitTest` (см. CI unit-test).
Сценарии (требуют тест-backend + устройство/эмулятор):
- пациент бронирует сам → запись в mobile API, владелец = пациент;
- регистратор бронирует за пациента → POST /appointments, owner = staff;
- offline-бронь → восстановление сети → replay по исходному маршруту;
- сервер отвечает 409/403 → статус Rejected, UI показывает «Отклонено», без повторной операции;
- отмена/undo неподтверждённой записи — без фантомных строк;
- очередь: подписка на `specialist_{id}::{date}`, частичное событие → REST-догон.

## Ограничения (честно)

- `service_id` в `VisitServiceOut` требует согласования на backend (сейчас — заглушка выбора).
- Одно WS-сообщение = одна комната: переключение специалиста/даты переподписывает сокет.
- Новые UI-строки пока не вынесены в strings.xml (i18n-долг).
- release-smoke в CI требует корректных секретов подписи (`ci-release.jks`) на стороне репозитория.
- Полная приёмка «мобильный + веб на тест-backend» требует живого backend и эмулятора — вне этой сессии.
